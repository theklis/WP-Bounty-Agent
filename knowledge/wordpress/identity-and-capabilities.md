# Identity, roles, capabilities, and account changes

## Authentication is only identity

WordPress uses authentication cookies and session tokens for browser login; cookie validation checks the embedded session token, which can be invalidated. `is_user_logged_in()` asks whether the current visitor has a user; `wp_get_current_user()` returns the current `WP_User` object. Neither grants permission for a particular operation. A plugin may also accept an application password, API key, bearer token, magic link, or custom session; trace how that credential becomes a WordPress user or plugin-specific principal and what authority is then assigned. WordPress [Application Passwords](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/) are available in core since **5.6** for programmatic authentication; they are not a replacement for endpoint authorization. [Sources: [cookie validation](https://developer.wordpress.org/reference/functions/wp_validate_auth_cookie/), [session token](https://developer.wordpress.org/reference/classes/wp_session_tokens/create/), [login state](https://developer.wordpress.org/reference/functions/is_user_logged_in/), [current user](https://developer.wordpress.org/reference/functions/wp_get_current_user/), [REST authentication](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/)].

**Audit question:** What establishes this caller's identity in this transport, and can a guest or a different logged-in user reach the same callback? Do not infer identity from a nonce, an email field, or a client-supplied user ID.

Authentication can be changed by filters. `authenticate` participates in credential validation; `determine_current_user` determines the current user for a request, including cookie-derived identity. If a plugin hooks either, inspect ordering, returned user/error/ID, and whether its custom token is bound to the intended account. These hooks establish identity context, not permission for a business action. [Sources: [`authenticate`](https://developer.wordpress.org/reference/hooks/authenticate/), [`determine_current_user`](https://developer.wordpress.org/reference/hooks/determine_current_user/)].

## Roles and capabilities

Roles are bundles of capabilities, not immutable trust levels. `current_user_can()` tests the current user's capability; `user_can()` tests a specified user. Primitive capabilities (for example, `edit_posts`) differ from meta capabilities (for example, `edit_post` for a particular post ID) that `map_meta_cap()` resolves using object context. An object-aware check must use the actual object that will be acted upon, after any attacker-controlled ID substitution. A broad capability, or a role-name comparison, may be inappropriate for a plugin-specific object. [Sources: roles](https://developer.wordpress.org/plugins/users/roles-and-capabilities/), [`current_user_can()`](https://developer.wordpress.org/reference/functions/current_user_can/), [`user_can()`](https://developer.wordpress.org/reference/functions/user_can/), [`map_meta_cap()`](https://developer.wordpress.org/reference/functions/map_meta_cap/).

Review read/create/update/delete separately: the capability for reading an object need not cover changing it; a check before a later object lookup can protect the wrong record. Follow custom capabilities and role grants across installation, upgrade, and settings code. A role string such as `shop_manager` is useful context, but the effective permission depends on assigned capabilities, filters, site context, and plugin rules. Searching only for `current_user_can()` misses custom access systems. Multisite has further differences; see [ownership and plugin models](ownership-and-plugin-models.md).

## Sensitive account operations

User creation and updates can change `role`, password, email, and privilege-relevant metadata. `wp_insert_user()` can set a supplied role; that API does not decide whether the caller may choose it. Trace which fields the caller controls, whether an existing user ID can be substituted, and whether an email/password/recovery change is verified through the intended channel. `WP_User::set_role()`, role/capability mutations, default-role settings, and plugin profile fields can create indirect escalation paths. [Sources: `wp_insert_user()`](https://developer.wordpress.org/reference/functions/wp_insert_user/), [roles and capabilities](https://developer.wordpress.org/plugins/users/roles-and-capabilities/), [options API](https://developer.wordpress.org/apis/options/).

For account recovery, follow token issuance, delivery address, account binding, expiry, consumption, and whether a prior email change can redirect recovery. A successful user update call does not prove the recovery flow authenticated the rightful account. [Source: [`wp_update_user()`](https://developer.wordpress.org/reference/functions/wp_update_user/)].

**What a successful login or capability check does not prove:** ownership of a selected order, booking, submission, or user; request integrity; correct permission for a different action; or the safety of later state changes. Continue with [ownership](ownership-and-plugin-models.md) and [nonces](nonces-and-tokens.md).
