## Source says: scope used for initial screening

The [program scope](https://www.wordfence.com/threat-intel/bug-bounty-program/) and [terms §2](https://www.wordfence.com/bug-bounty-program-terms/) list these categories. The vulnerability must have demonstrable security impact and meet exclusions; a label alone is insufficient.

| Category | Current listed types | All-tier installation floor and attacker prerequisite | Additional condition |
| --- | --- | --- | --- |
| High Threat | Arbitrary PHP file upload, read, or deletion; arbitrary options update; remote code execution; authentication bypass to Admin; privilege escalation to Admin | At least **25** active installations; unauthenticated or low-level authenticated (Subscriber/Customer) attacker | **25–999:** listed in the WordPress.org plugin repository. Non-repository/premium software below 1,000 is excluded by the terms. |
| Common and Dangerous | Stored XSS; SQL injection | At least **500** active installations; unauthenticated or low-level authenticated (Subscriber/Customer) attacker | **500–999:** listed in the WordPress.org plugin repository. The program page expressly excludes premium software below 1,000. |
| Other otherwise in-scope types | Subject to impact and exclusions, not a blanket acceptance of every class | **Standard: 50,000; Resourceful: 10,000; 1337: 500** active installations | Researcher tier must be known or outcomes compared by tier. |

The [terms §2](https://www.wordfence.com/bug-bounty-program-terms/) specify locally runnable free or premium plugins/themes. They exclude WordPress Core for bounty, vendor-hosted services or endpoints outside the locally run plugin/theme, non-WordPress.org software under 1,000 estimated installations or sales, products with their own developer-run public bug bounty or responsible-disclosure program, and plugins/themes closed to downloads or sales. The terms give a narrow closed-product exception when the reporting researcher found and responsibly disclosed the issue that caused closure and can prove it. The public [program page](https://www.wordfence.com/threat-intel/bug-bounty-program/) lists example excluded vendors and says its asset list is non-exhaustive. Check product and supplier status anew.

The [program FAQ](https://www.wordfence.com/threat-intel/bug-bounty-program/) says premium installation counts default to sales; absent sales data, Wordfence uses an internal estimate. A locally invented install count cannot establish scope. The same FAQ calls Administrator, Editor, and Shop Manager high privilege; the [terms' exclusion list](https://www.wordfence.com/bug-bounty-program-terms/) also excludes Contributor/Author and other roles granted by an administrator rather than a common default registration role. Verify plugin-specific role powers and actual attacker prerequisites; do not map a custom role by name alone.

The [program exclusions](https://www.wordfence.com/threat-intel/bug-bounty-program/) and [terms §2](https://www.wordfence.com/bug-bounty-program-terms/) include business-only logic flaws without direct security impact, DoS, CSRF, missing authorization/IDOR, basic disclosure, object injection without a usable gadget, open redirects, SSRF, hard-to-reproduce races, and stated low-impact or false-positive patterns. The terms also give consequential missing-authorization examples in tier qualification. **Research interpretation:** the exact exploit, effect, and category need careful checking; do not assume either that every authorization flaw is rewarded or that a meaningful authorization finding is technically invalid. These are Wordfence program classifications, not WordPress security semantics or CVE Program criteria.

## Source says: reporting and disclosure

The [terms §1](https://www.wordfence.com/bug-bounty-program-terms/) require a registered, authenticated researcher for bounty participation; Wordfence-only submission and no prior disclosure for reward; confidentiality through coordinated disclosure and public CVE release; and sufficient detail to validate the issue. The [program key rules](https://www.wordfence.com/threat-intel/bug-bounty-program/) require a valid working proof of concept for duplicate priority. Wordfence must handle disclosure for a reward under the [submission release](https://www.wordfence.com/threat-intel/bug-bounty-program/submission-release/). A CVE ID by itself does not guarantee a bounty; the first valid duplicate submission has priority. The terms prohibit developer reports about their own software for bounty participation.

The [terms §1 prohibited acts](https://www.wordfence.com/bug-bounty-program-terms/) require disclosure in the submission form if AI tools assisted at **any stage** of generating or assisting the report; AI-generated reports must be manually verified. They prohibit automated or large-scale AI-generated report submissions and warn of restrictions or bans for hallucinated, false-positive, or low-quality reports. **Research interpretation:** AI-assisted source review is compatible with a carefully tested report if the AI use is accurately disclosed; this project's stricter [human confirmation rule](../../../docs/findings.md) still applies. Use authorized local tests, never fabricated PoCs or bulk reports.
