# Specialist research playbooks

Use these **on demand** inside the [core audit methodology](../docs/audit-methodology/README.md). First model the target's actors, objects, state transitions, and deep-dive themes. Load the smallest set that helps investigate a consequential boundary; add a companion only when a traced path reaches it. The [WordPress knowledge index](../knowledge/wordpress/README.md) explains platform behavior, while these playbooks explain how to investigate a security theme. Recheck version-dependent semantics against the supplied source.

**Selection examples:** A booking audit may start with authorization, tokens, and business logic, then add commerce or chaining if the path reaches payment or a second handler. A backup audit may start with filesystem/archives and authorization, then add network if remote storage is reachable. A membership audit may emphasize identity, recovery, privilege, and state transitions. A REST-heavy integration may emphasize custom identity, tenant isolation, network requests, and webhooks. A simple rendering plugin may need only rendering/XSS. These are prompts for selection, not fixed bundles or scores. When impact is comparable, public and lower-privilege paths generally deserve earlier attention; current bounty eligibility is a separate, later intelligence question.

For any selected theme, write target-specific expected security properties in the local [audit record](../templates/audit-record.md). A missing enforcement point is an investigation question, not automatically a finding. Trace actor, reachability, control, transformations, distinct authentication/authorization/ownership/request-integrity decisions, sensitive action, and observable effect. Seek counterevidence. Record necessary premises as **supported**, **inferred**, **unknown**, or **contradicted** under the [evidence model](../docs/evidence.md); use the [finding lifecycle](../docs/findings.md). Only explicit human validation makes a finding **CONFIRMED**. Playbooks cannot upgrade status or bypass falsification.

**No matching family?** Derive hypotheses from the plugin's unusual trust model, custom protocol, or state relationships using the core method directly. Do not force a novel path into a predefined class. Keep target notes, test plans, and artifacts in ignored `research/`; target source remains read-only. These are research procedures, not executable commands or payload catalogs.
