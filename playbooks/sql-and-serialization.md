# SQL grammar and serialized data

## SQL: controlled value or controlled grammar?

Load this when a guest or lower-privilege actor can influence custom queries, table names, selected columns, sort expressions, search filters, or stored data later inserted into SQL. The invariant is that untrusted choices affect only the intended **values or allowlisted query shapes**, not arbitrary SQL grammar. Follow **entry or stored value → every cast/map/escape/prepare step → final query text and bindings → executed query → observable read or write**. Include custom query builders, fragment helpers, dynamic table prefixes, `ORDER BY`, identifiers, operators, `IN` construction, and second-order option/meta/custom-table inputs. The relevant boundary is the database parser, not the mere presence of `$wpdb`.

`$wpdb->prepare()` may correctly bind values while leaving a concatenated identifier or fragment outside its placeholders; conversely, concatenation of fixed trusted fragments is not injection. Inspect the *actual* format string, placeholder arguments, identifier allowlist, and installed WordPress version when `%i` behavior matters. For LIKE patterns, determine which characters are intended as data versus wildcard syntax. Counterevidence includes strict mappings from small input sets, integer casting that fully constrains a numeric position, and correctly bound values. A candidate needs evidence that the stated actor can change query grammar after all transformations, that the query executes, and that the changed query can cause a security effect. [Data/storage semantics](../knowledge/wordpress/data-and-storage.md) supply API details.

For safe local validation, compare a legitimate filter/sort against a controlled alternative using disposable records and observe the executed query or bounded result. Do not infer injection from an error string or a single escaping call; establish what the parser receives and what authority the query has. If the effect is another actor's data, pair with [authorization](authorization-and-isolation.md).

## Serialization: reconstruction versus exploitability

Load this branch when attacker-controlled bytes or a lower-trust stored value may reach `unserialize()`, `maybe_unserialize()`, import/restore processing, or a custom object hydrator. Trace **writer → stored representation → later reader → deserializer → classes available → magic methods or property use → effect**. Cross-request storage is often the important bridge. Distinguish control of a serialized string from control of an object instance; distinguish object creation from a consequential gadget or downstream property use. JSON parsing is not PHP object reconstruction by itself, but hydrated fields can still steer later security decisions.

Seek type restrictions, trusted-only writers, integrity protection, `allowed_classes` behavior where used, post-deserialization schema checks, and absence of reachable effect as counterevidence. A strong PHP object-injection claim needs a feasible class/method path and security outcome in the target environment; `maybe_unserialize()` alone is an observation. In an authorized local test, use benign test data to establish who can write the serialized value and which consumer/class path runs, then document the remaining gadget premise rather than assuming code execution. [Archives/imports](filesystem-and-archives.md), [configuration](privilege-and-configuration.md), and [execution](code-execution.md) are companions only if the trace reaches them.
