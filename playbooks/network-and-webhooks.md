# Server-side requests and external events

## Outbound request authority

Load this when a lower-trust actor can set a URL for image/feed import, webhook testing, remote backup, callback, API integration, or a stored job. Derive the rule for allowed destinations and response use. Trace **writer → URL storage/transforms → HTTP call → redirects/DNS/protocol handling → destination reached → response or side effect visible to attacker**. Record request method, forwarded headers/credentials, network position, and whether a response body, timing, or later stored result is observable. A user-controlled URL alone is not a severe SSRF claim; impact depends on reachable internal services and what the actor learns or changes. [WordPress HTTP knowledge](../knowledge/wordpress/files-and-network.md) explains safe and ordinary request APIs; verify actual filters and installed behavior.

Seek fixed endpoints, strict host/protocol policies, validation after redirects, bounded response handling, and lack of an attacker-observable effect. Consider redirects or host resolution changing between validation and fetch only when the implementation permits that transition. In an authorized local test, use controlled destinations to distinguish allowed versus blocked hosts and observe what result the plugin exposes. If the response discloses a credential or the request reaches another privileged surface, link [disclosure](information-disclosure.md) or [chaining](chaining.md) and prove that next edge.

## Inbound webhook trust

When an external event changes a local object, derive **sender authenticity → event integrity → correct external account/environment → intended local object → allowed transition → replay/duplicate policy**. Follow raw request/body through signature or shared-secret verification, event ID and timestamp handling, order/user/reference lookup, queueing, and downstream effects. A valid signature authenticates a payload source under a configured secret; it does not by itself prove the referenced order belongs to the right merchant, that an amount matches, or that a transition is permitted. Webhook delivery may be asynchronous and repeated; inspect idempotency and stale event handling.

Counterevidence may include verified signatures over the exact body, independent object/account binding, state guards, and duplicate-event records. A public webhook URL is expected; exposure alone proves nothing. Before a strong claim, identify how the stated attacker can supply or replay the event, which check fails, which local object is selected, and the consequential state change. In a local test, compare a legitimate event with a wrong signature, wrong object/reference, duplicate, and out-of-order event using test accounts and cleanup. For payment semantics use [commerce](commerce.md) and [WooCommerce knowledge](../knowledge/wordpress/woocommerce.md); for outbound webhooks, assess both destination control and information sent.
