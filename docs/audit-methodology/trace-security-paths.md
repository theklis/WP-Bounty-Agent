# Trace security paths: phases 4–8

## 4. Treat state as part of the path

Inventory security-relevant sessions, cookies, options, meta, custom tables, transients, caches, queued jobs, uploaded files, object IDs, invitation/reset keys, order keys, payment references, API keys, and other tokens when the target uses them. For each important item, trace **origin → who can set or learn it → storage → transformations → consumers → authority granted → expiry/revocation → later privileged use**. Ask whether a value written under one actor's authority is later read under another's. This is how a first request may change the security meaning of a later one. Load [token](../../knowledge/wordpress/nonces-and-tokens.md), [storage](../../knowledge/wordpress/data-and-storage.md), or [deferred-work](../../knowledge/wordpress/background-and-rendering.md) knowledge only where relevant.

## 5. Locate distinct controls

For every important action, answer separately: **authentication** (who is calling and how identity is established); **authorization** (may that actor perform the class of action); **object ownership/isolation** (may they act on this exact object, site, or tenant); **request integrity/anti-CSRF** (can ambient credentials be induced by a different origin and what does the nonce or equivalent prove); **semantic validation** (is this input valid for the workflow); and **destination/context safety** (is the transformed value safe at its precise use). Mark a control as present, absent, inapplicable, or unresolved with source evidence and scope. Do not substitute a login, capability, nonce, or object ID for another control. A WordPress nonce does not establish authorization. Platform-specific semantics live in [WordPress knowledge](../../knowledge/wordpress/README.md).

## 6. Follow data and authority to the effect

Trace **attacker capability → reachable entry → controlled input or state → transformations → relevant checks → sensitive operation/state transition → observable security impact**. Follow calls, object properties, hooks, filters, model helpers, storage writes and reads, and callbacks across files. Reconstruct interprocedural, second-order, deferred, and cross-request paths. At each hop, record the source location and target version; identify what the attacker can still choose after transformations. Trace authority as well as data: an authorized write can feed a privileged later read. If a required edge relies on framework behavior or configuration, test or mark it as an assumption.

Potential effects include object disclosure or mutation, role/option/account changes, database or filesystem effects, rendering, outbound HTTP, token disclosure, email or recovery behavior, and payment/order changes. A dangerous function is merely a point to investigate. The claim requires reachability, control, a failed boundary, and a meaningful impact under stated conditions. Work backwards from high-impact operations when the forward path is hard to see.

## 7. Derive invariants from the plugin's business rules

For each deep-dive theme, write the rules that must remain true across requests: who may create, see, change, cancel, pay for, export, restore, or consume an object; which transitions require prior states; what binds a token to an actor or object; and when authority must be rechecked. Probe out-of-order transitions, substitution of another user's object, independently changed price/status/role/owner fields, and values created in one trust context then consumed in another. Booking cancellation, membership activation, backup restoration, file management, and checkout are examples of different invariants, not a fixed checklist. Use the software's workflow to decide what deserves depth. Record derived rules in the [audit record](../../templates/audit-record.md), then ask whether a stated attacker could violate them during hypothesis generation and SECOND PASS. Unknown enforcement alone is not a finding.

## 8. Assemble and challenge attack graphs

Use a small conceptual graph when the path crosses components. Nodes can be actors, endpoints, objects, tokens, stored state, privileges, or effects. Edges state *can invoke*, *controls*, *writes*, *reads*, *discloses*, *authorizes*, *transforms*, or *triggers*. Label every necessary edge **supported**, **inferred**, **unknown**, or **contradicted** under the [evidence model](../evidence.md), with its versioned source or test reference. An unknown edge is an investigation question, not permission to complete the chain by assertion.

Look for **write here → trust there**, **issue token here → consume there**, **authorize object A → substitute object B later**, **low-privilege state → privileged job**, and **public primitive → sensitive primitive**. Check whether authority established at one step still applies at the next, whether an identifier is mistaken for a secret, and whether time or state changes after a check. A chain can combine individually harmless actions; a valid finding can also be a single request. Keep separate claims in separate [finding records](../../templates/finding.md) and link them when a chain depends on both.
