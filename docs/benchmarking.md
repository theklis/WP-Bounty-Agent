# Blind benchmarking and evaluation

BENCHMARK is a Codex-guided evaluation of the normal [Source Audit workflow](source-audit/README.md) against historical local source or a small synthetic reasoning fixture. It asks whether the audit discovered and reconstructed a known path, challenged it correctly, and placed it in a useful human-validation queue. It is neither a scanner nor a leaderboard. Natural-language requests such as `BENCHMARK <prepared local target>` and, after freeze, `COMPARE BENCHMARK <case/run ID>` need no command parser. Source Audit standards, [finding statuses](findings.md), and human confirmation rules remain unchanged. Do not test third-party production sites; any reproduction occurs only in an authorized local environment.

## Separation is the validity gate

Use two phases and, where practical, two separate contexts:

1. **BLIND (Context A):** receive only a neutral target handoff and source; run the ordinary audit; freeze its complete result. Do not open the coordinator manifest, ground truth, disclosure, fix, or comparison material.
2. **REVEAL (Context B):** verify the freeze, then read ground truth and compare it with the frozen audit. Context B may see both. Never edit the frozen result to improve its match.

Instructions to disregard an answer already seen do not restore blindness. If the answer, affected path, test assertion, advisory, or fix was exposed to Context A before freeze, the run is **INVALID for independent discovery measurement**. If prior model knowledge may identify the issue, record `POTENTIAL PRIOR-KNOWLEDGE CONTAMINATION`; the run may still assess workflow, but cannot be advertised as clean discovery. A separate context reduces conversation leakage, though it cannot erase model prior knowledge or enforce filesystem isolation. If genuine separation is unavailable, say so and use the run only for a limited workflow evaluation.

For a clean run, keep coordinator-only manifest details and truth outside Context A's readable files. A coordinator can hold them in a separate inaccessible workspace, or place them in the case directory only after freeze. The directory layout below describes the completed case, not permission to expose those files during BLIND. If shared filesystem access makes withholding impossible, record **LIMITED FILE ISOLATION** and do not claim clean independent discovery even when no deliberate truth read is observed. Actual answer exposure remains **INVALID**.

## Local case and run layout

All filled records and target files stay in ignored `research/benchmarks/`:

```text
research/benchmarks/<case-id>/
  manifest.md                  # coordinator only; withhold from blind-accessible files
  target/                      # historical source/archive or a reference to authorized local source
  ground-truth/truth.md        # withheld until freeze; never blind input
  runs/<run-id>/
    blind/                     # frozen copy of normal audit/finding records, made before reveal
    freeze.md                  # blind file inventory and hashes, written before reveal
    comparison.md              # written only after reveal
```

Use neutral case/run identifiers that do not encode a CVE, vulnerability class, endpoint, or expected result. The coordinator copies only the **blind handoff** fields from the [manifest template](../templates/benchmark-manifest.md) into Context A; Context A does not open the full manifest or enumerate the case directory. Exposure of a case type that reveals a positive or negative answer compromises clean measurement. The `target/` path may point to a preserved original archive or read-only source tree; follow [safe source intake](source-audit/intake-and-workspace.md). The [comparison template](../templates/benchmark.md) belongs in each run. Never overwrite a prior run.

The manifest's benchmark state is separate from a finding status: **PREPARED → BLIND AUDIT → BLIND FROZEN → REVEALED → COMPARED → COMPLETE**. Use **INVALID** when source identity, answer separation, or freeze verification fails. Keep contamination/isolation as a separate field: **none known**, **potential prior knowledge**, **known-answer regression**, **limited file isolation**, or **answer exposed**. A contaminated or known-answer run can be completed as a workflow exercise without counting as clean discovery.

## Prepare without leaking the answer

The coordinator records case ID, benchmark type, target name and exact version/commit, source origin and location, full source digest, permitted setup assumptions, allowed-information policy, ground-truth location, and run IDs. For a ZIP, record its SHA-256 and the extracted root; for a tree, record a complete deterministic file inventory with relative path and SHA-256 of bytes, plus an aggregate digest of that sorted inventory. A capped or incomplete helper digest is not a complete source identity. Record the methodology/tooling repository commit and whether its working tree is dirty; clean commits make later runs more comparable. Record which **CURATED** learning was available at that commit. At blind freeze, record material run conditions: model/agent and reasoning configuration where known, important available tools, actual web/documentation policy, meaningful time/context/effort limits, and human intervention during BLIND. Mark material unknowns `unknown`; do not invent internal details or require exact timing/token telemetry.

Supported types are historical known-vulnerability, rejected/false-positive, synthetic reasoning, and regression/known-answer. A synthetic fixture can test a specific control or state bridge, but cannot substitute for realistic historical targets. Before handoff, screen filenames, source comments, tests, changelogs, package metadata, and setup notes for spoilers. Do not rewrite supplied source to hide them; choose another input or mark the run invalid for independent discovery if they expose the answer. A known issue discussed earlier in the same research context or present in curated knowledge is not a clean discovery case. Do not expose case type or known issue count to Context A: a negative benchmark also must not announce that there is no bug.

Blind input may contain exact source/version, normal environment setup, authorization/scope, and ordinary public metadata that would be available in a real audit. It must not contain a revealing CVE ID, advisory title, vulnerability class, affected handler, patch diff, exploit, expected chain, truth record, answer note, or bug-naming test assertion. Default to **no vulnerability-specific web research** in the blind phase: platform/API documentation is allowed when needed to interpret code; searching the target name with CVE, vulnerability, advisory, or disclosure terms is not. Record any exception and its contamination effect.

The eventual corpus should vary authorization/IDOR, authentication/recovery, privilege escalation, rendering/XSS, SQL, file operations, token/state, network/SSRF, deserialization/code execution, business logic, WooCommerce/payment, chains, background work, and attractive false positives. Vary guest through higher-privilege actors, simple and large plugins, framework-heavy code, and single-handler versus cross-request paths. Do not optimize only for current bounty tiers. Target-selection quality and vulnerability-discovery quality are different evaluations; Target Hunter benchmarking is deferred.

## Run the ordinary blind audit

Context A follows [Source Audit](source-audit/README.md) and its [core methodology](audit-methodology/README.md), not an easier benchmark mode. Work in the ordinary ignored `research/audits/<audit-id>/` and `research/findings/<audit-id>-*` locations so safe ZIP intake and optional helper output retain their existing boundaries. Identify exact source and scope; model functionality, actors, objects, trust boundaries, and target-specific invariants; map applicable entries and deferred consumers; select playbooks; trace data **and authority** across handlers and stored state; form and falsify coherent candidates; prioritize the human-validation queue; record meaningful coverage; and perform a changed-perspective SECOND PASS. Use the existing [audit](../templates/audit-record.md), [finding](../templates/finding.md), and [validation-plan](../templates/validation-plan.md) records. Tool indexes are navigation leads, not runtime facts.

The auditor is not told that exactly one known issue exists, or that any issue must be found. Other valid candidates may exist. A source-backed **STRONG CANDIDATE** can enter the manual queue; **CONFIRMED** still requires explicit human reproduction. If access or time prevents a full audit, freeze the partial result honestly and do not count it as a completed discovery test.

## Freeze before reveal

Before anyone in the blind context reads truth, finish the ordinary audit workspace with audit record, candidate/finding and rejected-path records, coverage, second-pass delta, human queue, unresolved assumptions, and scope-limited summary. Recheck the complete target digest against intake; a changed source needs a new run or explicit revalidation before a clean result. Copy all material blind records, linked findings and validation plans, journals, and navigation output used into the run's `blind/` snapshot; record the original workspace paths. The target source is identified separately by its digest and need not be duplicated. Create `freeze.md` outside `blind/` with run/case ID, UTC freeze time, target version and complete digest, methodology/tooling commit and dirty-state note, contamination declaration, and a **sorted inventory of every snapshot artifact's relative path and SHA-256 bytes**. Record the exact file set, not only one aggregate hash. An optional aggregate SHA-256 over the canonical `path<TAB>digest<LF>` rows makes comparison convenient. Exclude `freeze.md` itself from that inventory. Before reveal, record `freeze.md`'s SHA-256 in an independent timestamped coordinator checkpoint outside the run directory, such as a retained message or read-only copy.

Verify the external freeze digest and recompute the full file set and hashes immediately before reveal and again when comparing. A mismatch, missing artifact, or retroactive edit invalidates the original freeze; preserve the evidence and start a new run if needed. Post-reveal corrections go in `comparison.md`, a local learning proposal, or a later run. Never patch the frozen `blind/` output to match truth. Standard local hashing tools or Python's standard library suffice; no benchmark-specific executable is needed.

## Reveal and establish ground truth

Only after freeze verification may Context B open `ground-truth/truth.md`, the public advisory, CVE record, source/patch, or researcher result. Use the separate [ground-truth template](../templates/benchmark-truth.md) to record affected versions, attacker prerequisites, entry, controlled data/state, transformations, checks and failed boundary, any cross-request bridge, sensitive effect, root cause, expected validation, and provenance. Label material premises **VERIFIED GROUND TRUTH** or **INFERRED OR INCOMPLETE GROUND TRUTH**; leave unknowns explicit. An advisory or CVE label alone is not a complete exploit path, and source/patch evidence may contradict advisory wording. Cite dates and exact versions where known. Public evidence can support comparison without requiring a new reproduction, but cannot upgrade a blind finding to **CONFIRMED** without the project's human-validation record.

Ground truth is a known-answer set, not a proof that no other issue exists. For a rejected/false-positive case, describe the exact suspected path and the blocking control under tested conditions; do not claim the entire product is safe. Compare technical findings independently of bounty eligibility, CVE assignment, or historical severity.

## Compare reasoning, not names

Use the [comparison template](../templates/benchmark.md) for each known issue or negative path. Match by the actual root boundary and path even when the blind wording or CWE differs. Compare relevant feature/surface, actor and prerequisites, controlled primitive, failed or effective control, each necessary chain edge, final effect, falsification, candidate survival, qualitative priority and likely researcher attention, validation queue, coverage, and SECOND PASS contribution. For every dimension record **YES / PARTIAL / NO / NOT APPLICABLE / UNKNOWN** and a short blind/truth reference. The table supports a narrative; it is not an aggregate score.

Use **WELL RECONSTRUCTED**, **PARTIAL PATH**, **RELATED SIGNAL**, **MISSED**, or **INCORRECTLY REJECTED** for a known issue. A negative path is **CORRECTLY REJECTED** only if the audit examined and defeated it; otherwise mark **NOT EXAMINED** rather than crediting falsification. These are comparison outcomes, not new finding lifecycle states. Keep clean-discovery validity separate from technical outcome. A blind audit that finds two primitives but misses their authority bridge is partial, not a complete chain. A first-pass miss recovered by SECOND PASS should be recorded explicitly.

For each significant extra blind candidate, distinguish **DISPROVED FALSE POSITIVE** (a necessary premise failed), **SUPPORTED**, and **UNRESOLVED BUT REASONABLE**. Absence from a historical advisory alone never makes a candidate false. Incomplete ground truth is an uncertainty, not a disproof. Diagnose actual false positives by the failed premise and reasoning error: sink-driven escalation, authentication/authorization or nonce/authorization confusion, assumed reachability or attacker control, missed ownership re-binding, overstated token authority, assumed chain edge or configuration, or misread framework/parser/rendering semantics. Retain useful observations. Diagnose misses by the first failure in intake/version, architecture, actor/object model, entry coverage, state/token inventory, data or authority flow, cross-request correlation, invariant, playbook selection, candidate formation, falsification, prioritization, partitioning, second pass, tool index, or setup/context. Record prior-knowledge contamination or failed blind isolation as a separate validity cause when it affects interpretation. Several causes may apply; categories guide method improvement, not blame.

## Use results without overfitting

The comparison ends with what the audit got right, missed, and got wrong; why; what reusable question would have found or falsified the path earlier; proposed learning; and a regression plan. Have the human researcher review the comparison and evidence before sending grounded results through [LEARN FROM RESULT](learning-workflow.md) as local **PROPOSED** lessons, patterns, or change candidates. Public ground truth does not itself supply a human reproduction record or bypass review, sanitization, or separate methodology/playbook approval. Do not turn one missed endpoint or function name into a permanent search rule; ask whether a proposed method works on another architecture and what false positives it might add.

Keep earlier runs intact. A same-target rerun after a method change is **REGRESSION / KNOWN-ANSWER**, with old and new methodology commits recorded; it can test whether the process now asks the right questions, but is not independent discovery. To test independent discovery of the same underlying reasoning improvement, use a different unexposed target. Across multiple runs, report raw counts with denominators for reconstruction, surface mapping, validation-queue capture, verified false positives, miss causes, and second-pass recoveries. **Independent-discovery denominators include only valid clean blind runs.** Report potentially contaminated or limited runs separately as workflow evidence, known-answer regressions separately as process checks, and invalid runs separately with exclusion reasons. Do not combine these classes into one discovery fraction or opaque agent score.
