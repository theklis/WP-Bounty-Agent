# Target Hunter

TARGET HUNT is a **Codex-guided research workflow** for choosing public WordPress plugin/theme software worth serious, authorized manual audit. It is usable now with available web and source access; there is no Target Hunter command, crawler, scanner, or automatic ranking engine. The output is an evidence-backed research priority, never a claim that a target is vulnerable. Research the software, not sites running it. Do not scan or test third-party production installations.

Start with the [research principles](../research-principles.md) and the [current-intelligence convention](../current-intelligence.md). Recheck the relevant [Wordfence program intelligence](../../knowledge/bounty/wordfence/README.md) and target metadata live before consequential ranking. Do not copy changing thresholds into this method or infer the researcher's tier. Load [WordPress knowledge](../../knowledge/wordpress/README.md) and [specialist playbooks](../../playbooks/README.md) selectively when a candidate's architecture calls for them.

| Funnel stage | Read | Decision or working result |
| --- | --- | --- |
| 1–3: define, discover, filter | [Discovery and filters](discovery-and-filters.md) | A manageable pool with sourced exclusions, conditions, and unknowns |
| 4–13: profile, investigate, form thesis | [Research and thesis](research-and-thesis.md) | Functional security profiles, history, saturation, testability, and light source reconnaissance |
| 14–16: prioritize and hand off | [Ranking, comparison, and refresh](ranking-and-refresh.md) | Ordered shortlist, selective audit themes, and exact-version handoff |

Use the compact [target profile](../../templates/target-profile.md) for serious survivors and the [hunt summary](../../templates/target-hunt-summary.md) for screened candidates and relative ranking. Filled records, downloads, and source extracts belong under ignored `research/targets/`; supplied source stays read-only. A focused hunt applies the same funnel within the requested class. A broad hunt spans functions and unusual plugin models rather than defaulting to popularity.

Usually recommend **3–7** strong candidates, fewer when evidence is thin. Explain why the first target deserves time before the second and which fact could change that order. If none earns deep audit time, say so and broaden discovery. [Core audit methodology](../audit-methodology/README.md) begins after selection; incidental suspicious code in reconnaissance is only a **POTENTIAL AUDIT LEAD** with uncertainty, never a confirmed vulnerability.
