# Drive a supplied source through the audit method

Use one [audit record](../../templates/audit-record.md) as the map, with versioned source references and a small set of selected themes. The approved [Core Audit Methodology](../audit-methodology/README.md) defines how to reason in each phase; this page gives the operating order and records to update for a real target. Return to an earlier step when new evidence changes the model. Do not turn navigation matches into findings.

| Operational checkpoint | Action and durable result |
| --- | --- |
| 0 — Intake and preflight | Follow [safe intake](intake-and-workspace.md). Record source identity, authorization, scope, workspace, dependencies, assumptions, exclusions, and any version-matched Target Hunter handoff. |
| 1 — Structural orientation | Read bootstrap/plugin header or theme entry, major modules, bundled libraries, models, admin/frontend/API boundaries, integrations, jobs, and security abstractions. Explain the structure before sink searches. Record a concise architecture map. |
| 2–3 — Model and surface map | Apply [model the target](../audit-methodology/model-the-target.md): purpose, actors, objects, relationships, states, sensitive effects, trust boundaries, and target-specific invariants. Map applicable direct, indirect, and deferred entry families below from registration to invocation. Record actor, prerequisites, controlled data, object, checks, downstream calls, state, and effect for important paths. |
| 4–5 — Themes and first pass | Select only architecture-justified [playbooks](../../playbooks/README.md) and [WordPress knowledge](../../knowledge/wordpress/README.md). Prioritize public/low-privilege paths, consequential authority transitions, custom controls, shared state, and high-impact operations. Record why lesser paths are deferred. |
| 6–9 — Controls, data, authority, and invariants | Apply [trace security paths](../audit-methodology/trace-security-paths.md). Resolve authentication, action authorization, exact-object ownership/isolation, request integrity, semantic validation, and sink/context safety separately. Trace controlled data **and authority** across calls, storage, handlers, tokens, jobs, and requests. Link writes to later reads, issuance to token consumers, and checks to the exact object ultimately acted upon. Probe whether a stated actor can violate each recorded invariant. |
| 10–13 — Candidate challenge and human queue | Apply [challenge candidates](../audit-methodology/challenge-candidates.md). Create a [finding record](../../templates/finding.md) only for a coherent, distinct security hypothesis; cite complete path evidence and weakest unknown premise. Search upstream, downstream, and framework counterchecks. Mark premises supported/inferred/unknown/contradicted, reject failed paths, and prioritize survivors **immediate / high / normal / low/defer** in the audit record's candidate queue. Prepare a [human validation plan](../../templates/validation-plan.md) for strong candidates; a plan is not a performed test. |
| 14–16 — Coverage, second pass, and summary | Use [coverage and review](../audit-methodology/coverage-and-review.md): track actors, boundaries, state systems, entry families, effects, and deferred partitions by reasoning depth. For a serious full audit, change both attacker perspective and analytical direction, then record new/rejected paths and coverage deltas. Finish with a scope-limited research summary and next manual actions. |

For the surface map, inspect only families the target actually uses:

- **Direct request entries:** authenticated `wp_ajax_*` and unauthenticated `wp_ajax_nopriv_*`; REST routes and permission callbacks; `admin_post_*` and `admin_post_nopriv_*`; frontend forms and direct handlers; custom routers/API endpoints; authentication, registration, account, password-reset, recovery, invitation, and identity hooks; upload, download, import, export, and backup/restore handlers; inbound webhooks, payment/IPN callbacks, and WooCommerce actions/endpoints.
- **Indirect consumers:** shortcodes, blocks, template/render hooks, and other hooks/callbacks that expose or consume security-relevant attacker-influenced state.
- **Deferred/background consumers:** cron tasks, queues/workers, scheduled reads of attacker-influenced stored state, and relevant CLI consumers when they participate in a security path.

For each applicable family, find registration and invocation, then establish who can reach it, prerequisites and controlled state, affected objects, checks, downstream effects, and any link such as low-privilege write → later cron, queue, or privileged render. This is a route to meaningful path tracing, not a requirement that every plugin implement every family or that a registered handler is vulnerable.

Use `rg`, symbol lookup, and basic parsing as navigation aids; inspect registration and surrounding control flow rather than emitting raw match lists. For each consequential path cite exact file, function/method, stable line or code context, and target version/commit. A dangerous sink, `$wpdb` call, REST route, or missing local nonce is an observation until reachability, control, failed boundary, and effect are shown. If source contains a new consequential subsystem outside the chosen themes, add it deliberately and update coverage.

Before opening a new finding, compare violated invariant, root cause, failed control, fix boundary, affected objects/endpoints, and exploit primitive against existing audit findings. Link multiple routes with one root issue; keep independent failures separate even if they share a CWE. A **POTENTIAL AUDIT LEAD** from Target Hunter follows the same evidence gate: locate cited code, reconstruct context, test reachability and checks, then promote to a hypothesis or record why it failed. Do not inherit the handoff's confidence.

Bundled dependency versions are context, not plugin findings by themselves. Establish inclusion, reachability, plugin-context effect, mitigations, and relevant eligibility before treating a dependency issue as a candidate. Keep technical validity and the [finding lifecycle](../findings.md) separate from current [Wordfence/CVE intelligence](../current-intelligence.md). A provisional scope note may help prioritize work, but final eligibility/CVE assessment follows human validation and requires fresh official facts. Only explicit human reproduction can make a finding **CONFIRMED**.
