# VALIDATE: manual candidate walkthrough

`VALIDATE <finding ID>` is a natural-language Source Audit handoff for a human researcher, not a CLI command, exploit runner, or finding-status change. Work only in an authorized local environment. Open the matching [audit record](../../templates/audit-record.md), [finding](../../templates/finding.md), and [validation plan](../../templates/validation-plan.md); verify their target/version, source identity, scope, actor, and current evidence before giving steps. If the plan is missing, draft it locally from cited evidence first. If the record is not a **STRONG CANDIDATE**, explain its missing premise. If a necessary setup fact is unknown, give the first discovery checkpoint rather than presenting later exploit steps as established.

## Build the handoff

Start with **What this feature does**: its legitimate purpose, normal users, important objects, ordinary workflow, and why the boundary matters. Assume the researcher knows security testing but has not used this plugin. Define necessary plugin terms. Follow with **What we are testing** in 2–5 plain sentences: actor, controlled value or state, expected control, suspected failure, and effect. Tie each material claim to the exact versioned source or an observed local request; do not invent menu paths, endpoint names, parameters, settings, or nonce origins.

List **What you need** as **Required** versus **Helpful**. Name only supported plugin settings, roles, accounts, objects, integrations, and local tools. Label actors consistently (for example, Account A — object owner; Account B — testing actor; Admin — later observer; Guest — unauthenticated). For uncertain setup write **Unknown — first determine how this feature is enabled** and give the smallest source or running-plugin check that would answer it. In **How to reach it**, give the verified UI path where known; otherwise use the normal workflow to discover and intercept the request before constructing one manually.

Break the claim into numbered necessary premises: reachability, attacker control, final object or state resolution, distinct authentication/authorization/ownership/request-integrity decisions, downstream consumer, and sensitive effect as applicable. For a chain, name every write → persistence → consumer → authority bridge. Test the cheapest premise that could defeat the claim first, while retaining impact and research value in priority. Give **Why test this first**, **Expected setup difficulty: LOW / MEDIUM / HIGH**, **Expected validation effort: LOW / MEDIUM / HIGH**, and **Main uncertainty** as workflow aids, not severity or bounty ratings.

## Run in checkpoints

Write numbered **Step-by-step validation** actions, grouped into short checkpoints. A typical order is (1) establish reachability and legitimate behavior, (2) prove control of one input or stored value, (3) test the specific security boundary, then (4) verify the final state or effect. Keep the complete intended sequence in the local validation plan. In an interactive `VALIDATE <ID>` response, briefly show the feature primer, hypothesis, required setup, and overall necessary premises, but normally detail only the next unresolved checkpoint. Wait for the researcher's observed, redacted result before giving later detailed steps; re-evaluate and revise those steps if the model changes, and stop if a necessary premise is contradicted. A trivial one- or two-action test may be shown in full, and provide the complete plan when the researcher explicitly asks for it.

Capture a legitimate baseline before altering security-sensitive input where applicable: use the normal UI as the stated actor, intercept in Burp, send to Repeater, replay unchanged, and verify the normal response and state. Change **one** relevant value at a time. Keep actor sessions distinct; identify which session cookie, bearer token, or nonce belongs to which actor without collecting or pasting its raw secret into tracked records. A nonce can help establish request integrity; it does not authorize an action. Compare both response and actual object/state, since a success message or HTTP status alone may mislead.

At important branches, say **If this happens** and the next discriminating action. A 403 may reflect ownership enforcement, an expired nonce, or malformed setup; inspect which check produced it before rejecting. If the object is unchanged, look for re-binding to the current actor. If a handler is unreachable, revisit reachability rather than declaring an authorization hypothesis false. A queued response requires checking the later worker, not treating queuing as the final effect. Distinguish **test setup failed**, **premise still unknown**, and **a necessary security premise was contradicted**.

For stored or cross-request paths, split the walkthrough into **Write phase**, **Persistence check**, **Consumer phase**, and **Final effect**. Show who controls the value, where it persists (session, option/meta, custom table, transient, queue, file, or other state), which later request/job/render/admin action reads it, and what proves the authority transfer mattered. A chain is supported only when each necessary bridge is observed or otherwise evidenced.

## Match proof to the candidate

- **Authorization/ownership:** compare a valid own-object baseline with another actor's object under separate sessions. Check the *final resolved object* and the action permission. An object ID is a locator, not a secret or permission.
- **Rendering/XSS:** identify input, any storage, exact HTML/attribute/JavaScript/URL output context, and victim view. Use a harmless local marker to test execution; do not seek credential or session theft.
- **SQL:** inspect the final grammar position, mapping, casts, escaping, and prepared bindings before testing. Use safe, nondestructive differential checks to determine whether the stated input changes query semantics; avoid destructive or denial-of-service probes.
- **Files, network, execution:** establish the minimum primitive separately from retrieval, destination, or execution. Use a researcher-controlled local or callback destination for network checks where appropriate; never target arbitrary third-party systems or require an internet callback when local evidence suffices. Avoid destructive effects, and stop once safer evidence resolves the premise rather than escalating automatically to shell execution.

State **Vulnerable result** as the exact observation that would support the hypothesis and **Blocking result** as evidence that a necessary premise failed *under the tested conditions*. Never conclude the whole plugin is secure. Include **If it does not work** with candidate-specific setup and blocker checks: wrong actor/version/object, disabled feature, stale nonce, format mismatch, upstream capability, ownership re-binding, queued work not run, or incomplete source/index assumptions. A failed test does not itself identify which explanation is true.

List **Evidence to save**: version/configuration, actor and object labels, baseline and changed requests/responses with secrets redacted, before/after state, relevant source lines, and each chain transition. Keep raw traffic and proof in ignored `research/`; collect no unnecessary credentials. Record the actual tester, date, steps, observation, and limitations in the finding's **Human outcome** section. Only explicit human reproduction supports **CONFIRMED**; a failed necessary premise supports a scoped **REJECTED** decision, and unresolved results remain unresolved. `VALIDATE` itself never changes status or bypasses the [finding lifecycle](../findings.md).
